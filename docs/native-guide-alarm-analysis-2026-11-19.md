# IAG 报警、引导总锁表示与逆向分析边界

日期：2026-11-19。范围为自由仿真操作台；其他模块继续使用原运行类和显示模式。原 EXE、配置和资源未修改。

后续用户新增实验记录及明确的操作边界已用于修正引导与解锁流程，见 [实验3和实验4逐项核对](console-experiments-3-4-audit.md)。新增的行为验证不等于原通信链已反编译完成；本报告中的机器指令证据边界保持不变。

## IAG 行车后的信息为何变成报警

X→IG 接车时，车轮进入 X 信号内方的第一个区段 IAG，X 正常关闭，进路锁闭继续保持。模拟行车仍按 2 秒间隔前进。这项关闭时机没有发生错误。

错误来自本项目的事件分类：`console_train.py` 把正常随车关闭记为 `signal_close`，`SimulationConsole.vue` 又把所有该类事件归入红色报警。现改记为 `train_signal_close`，保留在操作事件与回放中。失表示等异常保护关闭仍使用 `signal_close` 并进入报警区，没有删除保护条件或关闭时机。

## 引导总锁后的道岔单锁表示

后端此前已按咽喉计算 `guide_total_locked`，并拒绝该咽喉道岔的定位／反位操纵；前端只检查了手动 `manual_locked`，没有将引导总锁状态接入单锁绘制。

现自由台按“手动单锁或本咽喉引导总锁”绘制同一种红色空心锁闭标记，X、S 分别覆盖自己的咽喉。实际手动单锁与引导总锁保持各自状态；解除引导总锁不会清除原有手动单锁，其他咽喉不受影响。

## 本轮从原机器指令确认了什么

检查原上位机 `上位机.exe`，SHA-256 为 `f0cadb82538b3d73e28478a250e7787502e4918b7cad6bef1b2e23213f590501`。

原文件包含 `CSwitch` 的 RTTI 类名，缓存分析中可以识别虚函数入口。已进一步读取并导出：

| 原地址 | 机器指令支持的事实 |
|---|---|
| `0x412820` | `CSwitch` 输入刷新；其中 `0x412acd…0x412b45` 从状态字提取两个独立标志 |
| `0x412afd…0x412b18` | 状态字右移 2 位并与 1 相与，写入对象 `+0x108`，变化时置重绘标记 |
| `0x4118b0`，关键分支 `0x411a33` | 绘制时检查 `+0x108`，非零调用 `0x4111a0` |
| `0x4111a0` | 建立宽度 2 的画笔，调用 GDI `Ellipse`；参数 0 使用红色，参数 1 使用黑色擦除 |

在隔离的 x86 模拟器中执行原指令，结果如下。这里只替代外部 MFC／GDI 调用，不重写被测解码和几何计算。

| 输入状态字 | `+0x108` | `+0x10c` |
|---|---:|---:|
| `0` | 0 | 0 |
| `4` | 1 | 0 |
| `8` | 0 | 1 |
| `12` | 1 | 1 |

绘图探针实际捕获到红色 `COLORREF=255` 的画笔与 `Ellipse` 调用；擦除分支捕获到黑色画笔。原程序确实存在独立的锁闭圆圈绘制链。本轮未对 `+0x10c` 的完整业务含义作新增结论。

用于解释的伪代码如下，字段名与函数名由分析者命名，地址和位运算来自原机器指令：

```cpp
// CSwitch input refresh, recovered fragment, not original C++ source.
void refresh_lock_display(unsigned short status_word) {
    field_108 = (status_word >> 2) & 1;
    field_10c = (status_word >> 3) & 1;
}

// Recovered drawing branch at 0x411a33.
if (field_108 != 0)
    draw_lock_ellipse(/* clear = */ 0); // native 0x4111a0
```

证据保存在忽略目录 `outputs/simulator-rebuild/guide-alarm-audit-20261119/`，包括四个原函数反汇编、`4111a0.pseudo.c` 的自动分析伪代码、可复现探针和 `probe-results.json`。自动伪代码仍含地址和字段偏移，不能直接作为原工程编译。探针只执行选定的解码块与绘图函数，没有运行完整原联锁通信环境。

## 为什么先前测试通过，细节仍不一致

此前工作以原配置解析、部分函数逆向和规范重建为主。引导总锁的整条“操作输入→联锁状态→通信状态字→各道岔表示”链没有全部对照；报警区分类也属于我们自行实现的页面逻辑。这两处遗漏没有被先前测试覆盖。

199 条进路能在重建引擎中办理、行车和解锁，只证明那些测试场景通过，不能证明原应用全部状态、时序和显示已一致。上一轮把原共用 DG 名称推断为同步占用，同样属于超出证据的错误解释，已撤回并按用户确认的绝缘节修正。

可继续恢复的结构包括：RTTI 类、虚函数表、调用关系、字段偏移、状态位、资源命令、条件分支和计时逻辑，并据此形成有地址依据的伪代码。当前提供的文件中没有 PDB 符号文件；EXE 中的调试目录记录不等于附带完整符号。原变量名、注释、全部类定义及可直接编译的原工程不能由现有 EXE 精确还原。

仍未完整闭合的部分包括：引导总锁在原联锁机内对每个道岔寄存器的全部写入分支、原上下位机通信过程、异常输入组合与原应用界面的动态对照。因此本轮确认的是原锁闭标记的状态解码和绘制方式；总锁覆盖咽喉的界面行为还采用了用户本次明确提供的原应用观察，不能标记为整条原生链已反编译完成。
