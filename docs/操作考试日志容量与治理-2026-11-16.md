# 操作考试日志容量与治理方案

日期：2026-11-16。本文保留改造前的代码检查、只读数据库统计和容量规划。首期实现及最新实测见[实施记录](操作考试评价实施记录-2026-11-16.md)，两者应分别理解。

## 1. 当前结论

单份考试的点击日志通常不至于成为容量瓶颈；当前更值得先解决的是每秒重复传输完整日志，以及把累计运行事件随整段状态反复写入数据库。新增评分证据应使用结构化事件和精简状态差量，避免每次点击保存全站完整快照。

本次只读检查了`framework/backend/railway.db`，文件2,134,016字节，约2.04 MiB；页面大小4 KiB，共521页、其中13个空闲页。该库的操作会话、操作事件、考试、考试答卷、全屏事件和考试成绩相关表均为0行。因此：

- 不能把当前数据库总大小当作日志大小。
- 不能据该库计算真实单卷平均大小、P95大小或真实压缩率。
- 项目还有其他任务的测试库、备份和浏览器缓存，它们没有混入本次考试容量统计，也没有被清理。
- 本次未确认运行进程是否存在数据库环境覆盖，因此统计结论仅适用于上述明确文件，不宣称是线上或所有运行实例的数据。

## 2. 代码中已经确认的保存与传输方式

| 位置 | 改造前行为 | 影响 |
| --- | --- | --- |
| `app/models/operation.py` | 每次业务点击单独保存到`operation_events.content` | 原始操作证据，按点击数近似线性增长 |
| `app/services/operations.py:persistent_state` | `engine_state`中追加累计`runtime_events` | 同一会话越长，状态JSON越大 |
| `app/services/operation_runtime.py:pack` | 排除`history`和锁，但仍保存`session.events` | 最近运行事件与累计运行事件存在重复 |
| `simulation_console/runtime.py` | 内存最近事件最多500条；快照中附带最近60条；内存历史最多120帧 | 这些上限不能当成正式累计日志只有500条的依据 |
| `operations.py:response` | 调用`events()`取回并返回全部点击日志 | 每次响应体随累计点击增长 |
| `OperationConsole.vue` | 每1000毫秒同步状态 | 无新点击时仍可能重复接收完整日志 |
| `operations.py:refresh` | 活跃会话刷新后重新持久化状态并更新版本 | 即使没有业务变化，也可能反复重写较大状态 |
| `exams.py:detail` | 返回考试控制台和题目描述；学生按白名单排除标准日志 | 日志优化须保留该权限边界，同时避免反复传静态题目信息 |

`history`目前没有被`pack`持久化，不能说系统已经在数据库保存了每秒全站快照。`engine_state`是更新同一条状态记录，不是每秒必然增加一条永久快照；但重写仍有序列化、写事务、页更新及可能的日志开销，具体取决于数据库运行模式。

若累计事件长度为n且每次都重写此前全部事件，在均匀新增事件的简化条件下，累计序列化量呈1+2+…+n的增长。最终静态文件仍主要是线性体量，两者必须区分。

## 3. 单条与单卷大小估算

### 3.1 本次合成测量

使用当前点击事件字段制作了重复性较强的中文合成数据，在内存中进行JSON序列化和gzip压缩，未创建日志文件。以下不是学生真实数据，不含数据库行、索引、运行状态和评分记录开销。

| 点击数 | 紧凑UTF-8 JSON | 默认转义及空格JSON | 紧凑JSON的gzip |
| ---: | ---: | ---: | ---: |
| 100 | 38,387 B（约37.5 KiB） | 45,686 B（约44.6 KiB） | 1,179 B |
| 500 | 192,787 B（约188.3 KiB） | 229,286 B（约223.9 KiB） | 4,542 B |
| 2,000 | 773,790 B（约755.7 KiB） | 919,789 B（约898.2 KiB） | 16,873 B |

合成数据字段高度重复，压缩结果偏乐观，不能承诺真实日志也有这样的压缩率。中文转义、提示文字长短、参数、状态差量和异常信息都会改变大小。

### 3.2 规划预算

为了覆盖增加原因编号、业务事件、设备差量和关联字段的开销，容量规划先按每个持久化事件0.6—1.5 KiB估算。点击和自动业务事件要分别计数；以下“总事件数”是两者之和，不是点击数。

| 总事件数/卷 | 事件原文估算 | 加上初末状态、评分和索引预留后的建议预算 |
| ---: | ---: | ---: |
| 100 | 60—150 KiB | 约0.15—0.5 MiB/卷 |
| 500 | 300—750 KiB | 约0.5—1.5 MiB/卷 |
| 2,000 | 1.17—2.93 MiB | 约1.5—4 MiB/卷 |

这只是待压测的工程预算。数据库页利用率、索引、发布版本、长期事件格式和备份数量尚未实测，不能保证实际落在区间内。首期须用真实标准站合成考试轨迹测P50/P95/最大值。

按500事件/卷、0.5—1.5 MiB预算推算：

| 场景 | 在线有效数据预算，不含备份 |
| --- | ---: |
| 100名学生，一场考试 | 50—150 MiB |
| 1,000名学生，每年10场 | 约4.9—14.6 GiB/年 |
| 10,000份答卷，另保留两个完整备份副本 | 与在线数据合计约14.6—43.9 GiB |

压缩归档预计能进一步减少体积，但在有真实轨迹前，不用假定压缩率扣减上述磁盘预算。系统恢复备份与长期归档有不同用途，不应把每次备份永久累计。

## 4. 重复传输为什么更值得先处理

假设一场60分钟考试每秒轮询一次、500次点击均匀发生，每条点击约0.6 KiB，平均响应中携带约250条旧点击：

```text
仅重复点击日志 ≈ 3600 × 250 × 0.6 KiB
              ≈ 527 MiB/人/场
100人 ≈ 51.5 GiB/场
```

这是未压缩、均匀发生点击的演算，不是实测流量。开始时就积累大量日志会更大，点击集中在结束时会更小；HTTP压缩会降低流量，但不能消除查询、构造和解析完整历史的开销。以上还不包括站场状态和其他字段。

因此仅对下载日志做gzip，不能解决当前轮询接口的问题。短期优先改增量接口和无变化状态同步，再考虑更复杂的通信技术。

## 5. 推荐日志结构

### 5.1 四类内容分别保存

| 类型 | 内容 | 保存原则 |
| --- | --- | --- |
| 原始点击 | 按钮、目标、序号、结果、原因、事件ID | 服务端追加、不可改写；按事件ID幂等 |
| 业务事件 | 进路受理、锁闭、信号开放、取消开始/完成、拒绝、延时事件 | 一次变化写一次，关联点击及办理实例 |
| 关键状态 | 初始、截止、必要检查点以及设备差量 | 不按秒保存完整站场；检查点频率压测后确定 |
| 评价及发布 | 分项、片段、证据引用、版本、教师调整和已发布评语 | 引用原始证据，避免再复制一遍完整日志 |

业务事件至少包括会话内单调序号、类型、发生或生效时间、观察时间、来源、原因编号、设备标识、办理实例、关联点击及必要差量。延时事件的逻辑生效时间与服务器观察时间分别记录，不能用“后来刷新看见了”证明截止前已经完成。

客户端不决定事件是否接受、信号是否开放或状态是否恢复。故障、预置输入和系统自动变化必须有来源标记，避免错误归责于学生。

### 5.2 状态与历史分离

`OperationSession.engine_state`保留恢复会话所需的当前状态；正式完整历史放入独立事件记录，不再嵌入整个累计`runtime_events`随状态重写。最近提示缓存只保留必要的小窗口，并尽量由业务事件查询派生。

不是简单删除现有嵌入事件：需要先迁移、校验数量与哈希、验证恢复及原日志导出等价，再逐步切换读取。首期可以暂时保留原格式兼容层，但不得长期双写完整历史。

评分主要读取已记录事件和截止状态，不依赖重新执行所有历史点击获得当前事实。回放用于复核时，要使用对应引擎、时间及数据版本；不能只重新按按钮就宣称可靠复现。

### 5.3 增量读取

- 静态站场、题目和标准示范按版本加载，避免每秒重复返回。
- 状态同步返回状态修订号、必要倒计时及变化信息；无变化时返回轻量结果。
- 点击及业务事件分别使用`after_sequence`游标增量读取；日志面板分页，默认每页50条。
- 点击提交返回当前事件确认和必要状态，不重新加载完整历史。
- 断线重连按游标补齐；发现缺口再请求指定范围，不丢失旧证据。
- 限定单页上限和索引查询范围，服务端不能先全表加载再在内存切页。
- 首期保留HTTP轮询；SSE/WebSocket在HTTP方案压测仍不满足时再评估。

## 6. 压缩、归档与保留

建议策略如下，是项目配置建议，不宣称是学校法定保留期限：

| 资料 | 建议策略 |
| --- | --- |
| 正在作答、待评分或存在申诉的考试 | 完整在线，不做证据删减 |
| 成绩发布后且已超过课程规定申诉期的答卷 | 具备归档条件；默认在线窗口建议180天，取它与申诉保留期较晚者 |
| 归档证据 | gzip JSONL＋清单；保留题目/评分/引擎/站场版本及校验哈希 |
| 最终成绩、发布版本和审计 | 在线保留，期限依学校制度；不能因日志归档删除 |
| 自由仿真 | 按现有要求只保留当前内存会话回放，不纳入考试归档 |
| 操作学习 | 首期保持现状；今后单独确定保留策略，不套用考试删除规则 |
| AI草稿 | 每个评价修订只保留当前草稿、状态及次数，不保存全量提示词或多份无效响应 |

归档在项目内规划路径为`.runtime/exam-archives/`，备份为`.runtime/exam-backups/`。二者是有用途的正式运行资料，不是应在任务交付后删除的临时文件，且不得提交Git。上线前检查现有忽略规则，不假定目录名以点开头就不会上传。

安全迁移顺序：生成归档→校验事件数量/序号/哈希→从归档恢复并对照评分→登记索引→满足保留条件后，才允许移除在线原始事件副本。归档失败、申诉冻结、校验不通过时不得删除在线证据。

压缩归档不等于永久删除。任何永久删除政策另行确定，不能由本次规划自动实施。备份优先使用支持一致性快照的方式；不能直接复制正在写入的SQLite单个主文件就当作完整备份。数据库整理应在维护窗口执行，不在考试写事务中做压缩、备份或VACUUM。

## 7. AI不会放大全量日志

AI只接收教师确认的结构化评价摘要，建议输入不超过16 KiB UTF-8，输出最多500字；这是应用层长度预算，不等同于模型token上限。摘要超限时优先保留关键事实和必要扣分依据，无法完整表达则转人工评语，不能截断后编造。

不上传全站JSON、全部点击日志、逐秒快照、身份和口令。按摘要哈希与成绩修订缓存一份评语草稿；新修订使旧响应失效。AI调用次数设单卷上限和教师显式重试入口，不随轮询、打开页面或刷新自动重复调用。

## 8. 建议验收指标

以下为目标，尚未达到或经过压测证明：

| 指标 | 目标 |
| --- | --- |
| 正式历史记录 | 原始有效点击和应记录业务事件完整，事件ID不重复 |
| 无变化同步 | 2000次点击后的同步不包含全部旧点击；响应大小不随历史条数线性增长 |
| 标准站静态载荷 | 同一版本初始化后不按秒重复发送 |
| 每卷日志 | 分别报告500和2000总事件的原文、DB分摊、归档大小和评分时间 |
| 无变化响应预算 | 目标≤4 KiB应用层未压缩JSON，单独统计倒计时与状态字段 |
| 日志分页 | 索引游标查询，默认50、最多200条，不在服务端一次加载全部 |
| 100并发参考目标 | 约1次/秒状态同步＋每人平均5秒一次点击；状态/点击API P95≤300 ms；必须记录硬件、数据库模式和锁等待后才能认定 |
| 归档恢复 | 数量、顺序、哈希与关键评分结果一致 |

若达不到并发目标，先定位整段状态序列化、每秒写事务、全局锁和SQLite写锁等具体瓶颈，再决定缓存或数据库调整；不以更换技术名称代替测量。
